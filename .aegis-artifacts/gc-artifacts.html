Aegis SA / Coverage analysis

What GC expects, and what Aegis SA is missing

Eighteen Government of Canada security assessment artifacts measured against the app as it stands. Two are nearly free to render, three whole process steps are absent, and none of it needs a new project stage.

8 phases SRTM · SAR · SCP categorize · plan · monitor no new stages

First, a naming correction worth making before it reaches the UI: the artifact is the SRTM — Security Requirements Traceability Matrix. SRCL is a different thing altogether, the Security Requirements Check List for a contract, and it sits outside a system's SA&A package.

The findingThe front and the back of the process are missing

Aegis SA runs intake → scope controls → gather evidence → determine → package → POA&M → authorize. The GC process runs categorize → select and tailor a profile → plan the assessment → assess → report → authorize → monitor. Laid against each other, the app is strong exactly where the work is hardest and absent at both ends.

Phase 1Two reports you can almost already render

The SRTM and the SAR are the artifacts GC assessors ask for by name, and you hold most of what they need. Five per-control fields close the gap — and the most important of them, implementation_statement, is what your AI guidance feature is already most of the way to drafting.

Phase 5Cloud: the controls you do not own

The Cyber Centre assesses commercial cloud providers and publishes reusable reports precisely so departments can focus on their own internal SA&A. An app that cannot say “this control is the provider's, and here is the assessment it is inherited from” forces a department to self-assess controls it has no visibility into — which is both wrong and unsellable for any SaaS system.

The one commonly listed artifact that is not really a GC artifact

The System Security Plan (SSP) is NIST-native. In GC practice its content is spread across the security control profile, the system description and the SRTM, and it surfaces mainly in cloud and CSP contexts. Build rows 3, 5 and 10 and you can render an SSP if a user asks by name — but do not start there.

StructureWhat this means for the model

BackboneArtifacts become first-class

Eighteen types is past the point where per-method templates suffice. One registry with version, status, classification, language and a content hash over the source data.

PayoffStaleness becomes detectable

The content hash lets the app say this SAR is stale, findings changed after it was rendered. In an audit that is the difference between a tool and a folder of documents.

ChangeClose stops being terminal

Monitoring means authorized systems come back. Model it as re-entering assessment with a reassessment flag, so the same sub-steps and templates apply on the second pass.

ReuseCategorization feeds the SoS

Categorization is upstream of HTRA and answers to its own TBS standard. Let the statement of sensitivity reuse its injury values rather than replacing them — don't merge the two.

DerivationProfile selection stops being asserted

Once categorization is a recorded step, the PBMM proposal can cite it as its reason instead of being a scoping guess the user has to trust.

TestThe nineteenth artifact

Adding one more artifact type should need a template and a registry row, no application code. Same test as the ISO 27005 one in the HTRA brief.

HonestyWhat is verified and what is not

Confirmed against GC sources: SRTM, SA&A Plan and Security Assessment Report are named SA&A artifacts in a Shared Services Canada audit, which usefully distinguishes project artifacts from SA&A artifacts; control profiles live in ITSG-33 Annex 4/4A with a separate profile for cloud-based GC services; security categorization has its own TBS standard; the CA family includes CA-7 Continuous Monitoring, CA-8 Penetration Testing and CA-9 Internal System Connections; the PIA Directive was rescinded in October 2024 and replaced by a Standard with a mandatory template; and SRCL is TBS/SCT form 350-103.

Read the primary sources before seeding anything

I could not open ITSG-33 Annex 2 or the TBS appendices from this environment, so these remain unverified: the exact ISSIP activity names and their outputs, the injury scale labels in the Standard on Security Categorization, whether Appendix B is still current, the cloud guardrails validation deadline, the PIA template's field list, and whether any reauthorization interval is mandated at all. Apply the same discipline as the HTRA scales — seed as draft, stamp a source_ref, and show the draft state in the UI.
