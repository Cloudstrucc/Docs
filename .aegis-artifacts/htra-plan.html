Adding HTRA without refactoring Aegis SA

One conceptual change — method types — plus additive tables. The project pipeline, the stage machine and the existing control-compliance path stay exactly as they are.

7 phases Express · Handlebars · Svelte SQLite on Azure App Service no new project stages

HTRA is not another control catalogue, so it cannot be added as another row in the framework list. It is an analytic methodology that values assets by injury, assesses threats, and derives a residual risk a business owner signs for. The whole trick is to generalise what an assessment can contain rather than to change how a project moves.

The changeOne new indirection, one convergence point

Today a framework is a control list: an assessment scopes controls and records compliance state. HTRA has no controls at all. Rather than special-case it, give the framework registry a method_type and let the assessment stage ask each scoped method what it needs. Both method types then converge on a single finding table, which is what lets the decision package stay untouched.

ProcessHTRA's phases are sub-steps, not stages

The strongest temptation here is to add stages for the TRA phases. Don't. A method declares sub-steps, and the assessment stage renders whichever sub-steps its scoped methods declare. That one rule is what makes the platform configurable for any future methodology — ISO 27005, NIST 800-30, FAIR, or ITSG-33's successor.

ArchitectureWhere the pieces live at runtime

The derivation engine is the one component worth isolating: pure functions over scales and matrices, no database coupling, exhaustively testable. Everything configurable lives in SQLite as data, so a department tailoring its tables changes rows rather than code.

DataThe chain that makes a rating defensible

This is the query that an assessor's question reduces to, and the reason to link vulnerabilities to controls rather than keeping HTRA and ITSG-33 in parallel silos. One assessment then produces a TRA that justifies the control profile it selected.

SafetyThe AI gate

AI makes this module genuinely good, because the architecture document you already parse for control scoping contains most of what HTRA's first two phases need: data types and classification, components and stores, exposure and trust boundaries, stated controls. The constraint is that a TRA is a signed document, so no machine-derived value may reach it unreviewed.

The real test of the abstraction

Seeding a second risk-analysis method — ISO 27005, as an experiment — should require a new definition row and templates, and no new application code. If it needs code, the method interpreter leaked something that belonged in data. Build that test into phase 4 rather than discovering it later.

RisksFive ways this goes wrong

Phases become stages

The most likely refactor, and the one that breaks universality. Sub-steps are declared by the method; the stage machine never learns HTRA exists.

Risk bands get normalised

An HTRA Medium and an ISO 27005 Medium are different objects. Keep method-native scoring; any portfolio rollup is a separate view labelled approximate.

The arithmetic gets “fixed”

Multiplying ordinal scales is shaky and the urge to improve it is strong. Assessors compare against the published tables — report the official band, not a raw product.

The threat catalogue goes cyber-only

HTRA is all-hazards: deliberate, accidental and natural, against assets, services and people. An IT-only catalogue fails review.

Definitions get evaluated

Method definitions are admin-editable data. A single new Function on a derivation expression turns the admin screen into remote code execution.

i18n is retrofitted

GC deliverables need EN and FR. Translating scale labels through a method definition after the fact is painful; make the definition bilingual from phase 1.

OpenWhat to confirm before coding phase 1

  • The published scales. Level counts, level labels and every matrix cell must come from the TRA-1 publication, stamped with a source_ref naming the table. Until then the seeded method stays is_draft = 1 and the UI says so. The scales shown in the mockups are structurally right and numerically provisional.
  • ITSG-33's successor. The ITSP.10.035 / .036 / .037 series replaces ITSG-33 and broadens scope to OT and privacy. Departments are mid-transition, so both need to be supportable — which the method registry gives you for free.
  • Where the framework table really is, and whether a method view over it beats a rename. Prefer the view: renames touch every existing query.
