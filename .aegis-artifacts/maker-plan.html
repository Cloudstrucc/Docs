Aegis SA / Maker architecture

A configuration platform, without becoming a programming platform

Twelve definition types, four fixed enumerations, and one rule that keeps the whole thing testable. Design only — nothing to be built until the open decisions are answered.

10 phases blueprints · scopes · rules REST + Node/.NET SDK HTRA becomes blueprint #1

The HTRA work already proved this pattern once: control frameworks and risk methodologies are different method types over a shared metamodel, and their phases are method-declared sub-steps rather than new stages. Maker is that same idea applied to fields, artifacts, rules and views.

The governing rule

A fixed metamodel with configurable instances. Configuration selects and parameterizes from a vocabulary the platform defines; it never invents new kinds of things, and it never executes code. A blueprint may declare a new field, but not a new field type. A new step, but not a new stage. A new rule, but only from a closed set of action verbs.

MetamodelTwelve definition types over four fixed enumerations

ResolutionFour scopes, one resolved configuration, one hash

A blueprint installs at any scope. Resolution is most-specific-wins for whole objects like scales and templates, but a union for fields, steps, rules and fragments — a scale merged field-by-field is incoherent, whereas fields must accumulate.

The hard partShipping v2 of a blueprint the customer has edited

This is the feature that kills platforms like this one. You ship a GC blueprint, customers tailor it, then you publish an update. Without a real merge you either clobber their tailoring or you can never ship again.

Scale changes are declared, never inferred

Every stored rating references a scale level by number. Taking a scale from five levels to four requires an explicit mapping in the migration, or the upgrade is rejected. And changing a matrix cell does not recompute findings already assessed — a signed artifact's numbers must not move under it. That default belongs in the UI text, not just the code.

The key askExtending a report you did not write

"Choosing a template should add the control fields and update the existing reports." That is an artifact_fragment: a template declares named anchors, and a fragment patches one with a structural operation the renderer understands — not a string substitution, which would break the moment the base template was reformatted.

RulesConfigurable state changes, with a hard boundary

IntegrationDynamic schema forces code generation

A configurable platform cannot ship a hand-written typed client, because the types depend on the customer's configuration. So each SDK is a thin stable core plus a generated layer, and one endpoint makes it possible.

This changes the HTRA sequencing, deliberately

The HTRA brief phased HTRA as direct implementation. Don't build it that way now. Build Phase 1, then express HTRA as blueprint #1. HTRA arrives later than it would have, and in exchange you get an engine instead of a feature — and the GC control extension that follows costs a fraction of what it would have. The thing to protect: Phase 1 contains only what HTRA needs. If it grows a rules engine, a UI and an API before one blueprint exists, the plan has failed in the exact way this document warns about.

DisciplineWhat not to build

No code execution, anywhere

Rules, derivations, templates, prompts. One whitelisted evaluator, one audit surface. An admin screen that runs code is remote code execution with extra steps.

No new stages, ever

Steps are configurable; the four stages are the product. Every request to add one is a request to become a workflow engine.

No visual designer in Phase 1

JSON with validation and a preview is enough for the two blueprints that prove the engine. An editor built over an unproven metamodel shapes the metamodel around what was easy to draw.

No fragment deletion

Additive only. A blueprint author cannot know what a downstream regulator needs in a report. To change a base report, override it.

No implicit migration

Scale and field changes are declared or rejected. Guessing a level mapping silently rewrites assessed ratings.

Not a general app builder

Aegis SA configures security assessment, not arbitrary business process. Say no to the first customer who asks for a CRM, and keep a visible list of rejected metamodel extensions.

Decide firstNine open questions

Three change the schema, so they come first. The rest shape the product and the commercial model.

  1. Is program a real scope now, or reserved? Adding a ladder rung later invalidates every stored resolution. Recommendation: build it, hide it.
  2. Does an override store a patch or a full copy? This plan assumes a patch, because the three-way merge depends on it.
  3. Are historical findings ever recomputed when a matrix changes? This plan says no by default — the alternative changes what the derivation trace is for.
  4. Naming: Maker and Blueprint, or something else? It lands in the API namespace, so it is expensive later.
  5. Who may author configuration? One admin role, or separate author and publisher roles? Regulated customers will want the split.
  6. Can a project-scope definition exist without ever being a blueprint? Recommendation: yes — most tailoring is one-off, and forcing packaging would kill adoption.
  7. Multi-tenancy: one database per workspace, or shared with a tenant column? Interacts with the SQLite write limit and with how resolution is cached.
  8. Is the blueprint library a differentiator or a product line? Determines whether Phase 10 ever happens.
  9. Do the SDKs ship with the API or a release later? An API without an SDK invites integrators to hard-code a schema that is configuration — support load that looks like bugs.
